## Original issue body

# Problem

When a manuscript is authored across subdirectories (for example `part0/`, `part1/`, `part2/`, ...) and the user invokes folio with a multi-directory input glob such as `folio manuscript 'part?/ch??.md' out.pdf`, the config loader silently falls back to preset defaults instead of loading the user's `script.yaml` from the manuscript root.

Root cause: `internal/manuscript/run.go` computes `sourceDir` as `filepath.Dir(inputSet.Paths[0])` — the directory of the **first** input file only. `internal/config/config.go`'s `Load()` then reads `filepath.Join(LocalDir, \"script.yaml\")` — a single-directory lookup. If that specific directory has no `script.yaml`, the local overlay is silently `nil`, no error is raised, and folio uses the embedded preset (`presets/british-manuscript.yaml`) as if the user had configured nothing.

For a multi-part manuscript with a project-root `script.yaml`, this means the config only loads when the first input happens to sit in the same directory as `script.yaml` (or the source dir happens to symlink to the root). Any subdirectory-first glob (e.g. `part0/` alphabetically first) breaks the load with no diagnostic.

# Reproduce

Layout:
```
manuscript/
  script.yaml          <- user's real config
  part0/
    ch00.md
  part1/
    ch01.md
    ...
```

```
cd manuscript
folio manuscript 'part?/ch??.md' out.pdf
```

Emitted Typst uses the preset default `page-header.format: \"[title] • [chapter] • [author]\"` and preset default `font-size: 10pt`, regardless of what `manuscript/script.yaml` says. The user gets no warning; the fallback is silent.

Confirmed via direct call: `manuscript.LoadConfig(\"/manuscript\", opts)` returns the correct values, so the loader itself works — the failure is entirely in which directory is passed as `LocalDir`.

# Regression coverage

- RT-B1: Given a `script.yaml` at project root and inputs from `project/part0/`, the loaded config reflects the values in `project/script.yaml`.
- RT-B2: Same layout, inputs from `project/part1/` — same config loads.
- RT-B3: Given a `script.yaml` at project root AND a `script.yaml` in `project/part1/`, an input from `project/part1/` loads the **nearer** file (`project/part1/script.yaml`) — nearest-wins, no double-merge from the walk-up.
- RT-B4: Given no `script.yaml` anywhere on the walk path, loading succeeds and uses the embedded preset unchanged (backwards compatible with the no-local-config case).
- RT-B5: The walk stops at the user's home directory (or at the filesystem root, whichever comes first) — it does not read from `/etc/` or other system paths.
- RT-B6: The walk applies equally to the style-suffixed sibling override (`script-british.yaml`, `script-us.yaml`) so those are found in the same walked directory as the base `script.yaml`.
- UT-B1: A human reviewer runs a multi-part manuscript with subdirectory inputs and confirms the project-root `script.yaml` values (header format, font size, etc.) land in the PDF.

# Solution design

## Walk-up lookup

In `internal/config/config.go`:

1. Introduce `findScriptYAML(startDir, home string) string` that walks upward from `startDir`, checking each ancestor for `script.yaml`. Returns the absolute path of the first hit, or empty string if the walk reaches the home directory (or filesystem root) with no match.
2. Replace the direct `readOptional(filepath.Join(opts.LocalDir, \"script.yaml\"))` call in `Load()` with a call through `findScriptYAML`.
3. Apply the same walk to the style-suffixed sibling override so both the base and the suffix are read from the same discovered directory (nearest-wins is unambiguous only if both files are looked for in the same location).
4. Never walk above `$HOME` — this is a safety boundary. The user's global config already lives at `$HOME/.config/first-folio/script.yaml` and continues to be read separately.

## Backwards compatibility

- If `script.yaml` exists in `LocalDir` itself, behaviour is unchanged (walk finds it on the first step).
- If no `script.yaml` exists anywhere on the walk path, behaviour is unchanged (embedded preset only).
- The walk is bounded (does not traverse past `$HOME`) so the change cannot introduce surprise reads from unrelated projects.

## Diagnostic (optional)

Consider adding a `--verbose` or dry-run log line naming which `script.yaml` was loaded (or noting \"no local script.yaml found\"). This is out of scope for the bug fix itself but would prevent this class of silent-fallback confusion in future.

# Documentation impact

Update `docs/config.md` under \"Local configuration\" to state that `script.yaml` is discovered by walking upward from the first input file's directory until either a `script.yaml` is found or the home directory boundary is reached. Note that the nearest file wins (no merging of multiple walked files).

# Notes

Discovered when a user's real manuscript with `part0/ch00.md` (alphabetically first in the glob) triggered a silent config fallback. The manuscript rendered with preset defaults, and the user reasonably interpreted the mismatch as \"my config is broken\" or \"folio is buggy\" — the actual failure was invisible because folio raised no diagnostic and the preset defaults are perfectly valid.

This bug interacts with the separately-filed `font-style` on header/footer bug: both look like \"my config isn't taking effect\", and diagnosing one without the other is genuinely confusing.
