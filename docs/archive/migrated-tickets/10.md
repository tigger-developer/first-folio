## Original issue body

## Problem

First Folio now has two runtime architectures:

- `folio convert` and `folio letter` run through the Perl `bin/folio` dispatcher, Perl parsers/configuration/renderers, and substantial Typst string assembly.
- `folio manuscript` runs through a separate Go helper dispatched by the Perl executable.
- Most regression coverage is implemented as long shell scripts, while manuscript coverage is primarily Go.
- Build, install, version stamping, and release tasks still assume the split runtime.

This split duplicates CLI and configuration responsibilities, makes cross-mode behaviour harder to prove, and leaves production rendering logic embedded in dynamically assembled Typst. Moving only the Typst heredocs into template files would improve readability but would retain the underlying split and its duplicated orchestration.

## Goal

Migrate First Folio's product runtime and automated regression suite to Go behind one stable `folio` executable. Preserve the existing public contracts and generated-document behaviour unless a change is explicitly accepted in another issue.

At the end of this issue:

- `folio convert`, `folio letter`, and `folio manuscript` are subcommands of one Go binary.
- Go owns argument parsing, configuration, input resolution, document models, conversion, rendering, Typst execution, diagnostics, and exit status.
- Substantial Typst layouts are file-backed templates.
- Go tests replace project-owned Perl and shell regression logic.
- Perl is no longer a runtime, build, test, installation, or release dependency.
- Project shell is limited to simple build-tool recipes; it contains no application logic, complex control flow, generated-language heredocs, or test harnesses.

## User-Facing Contract

The migration must retain:

- The `folio` command name and the `convert`, `letter`, and `manuscript` subcommands.
- Existing options, positional arguments, defaults, output deduction, stdout/stderr behaviour, exit status, `-h`, `--help`, `--version`, `--dry-run`, and TTY safeguards.
- Org, Markdown, Fountain, Typst, and PDF support currently promised by each mode. Fountain remains excluded from manuscript input.
- UTF-8 and localized metadata, including names such as `Taḋg`.
- Existing `script.yaml`, style-specific YAML, global/local layering, root defaults, and mode-specific overrides.
- A4 defaults and the current British/US preset inheritance model.
- Existing document contracts, formatting semantics, warnings for lossy conversions, and hard errors for invalid input.
- Existing installation and Homebrew user experience.

Any intentional contract or layout change requires its own accepted issue and must not be hidden inside migration parity work.

## Solution Design

### Executable and packages

Replace the Perl dispatcher and separate manuscript helper with `cmd/folio`, producing one executable. Keep subcommands thin and move behaviour into focused packages. The final package boundaries should cover:

- CLI dispatch and common diagnostics.
- Typed layered configuration shared by all modes.
- Input/output format detection and validated path handling.
- A typed stage-play document/event model used by script conversion.
- Org, Markdown, and Fountain script parsers and emitters.
- Cover-letter parsing and rendering.
- The existing manuscript engine, integrated rather than launched as a helper.
- Typst-safe rendering and compilation shared where semantics genuinely match.

Do not force scripts, letters, and manuscripts into one document model where their semantics differ. Share infrastructure such as configuration, escaping, subprocess execution, and template loading without erasing mode boundaries.

### Typst rendering

Store substantial Typst layouts as parseable files under `templates/`. Go prepares typed template data and owns context-specific escaping for:

- prose and metadata;
- Typst string literals;
- raw and code text;
- URLs and footnote content;
- font names, dimensions, weights, and other validated configuration values.

Templates own layout; Go code owns data and policy. Generated Typst must not be assembled through large interpolated strings or heredocs.

### Configuration

Create one typed configuration loader using `gopkg.in/yaml.v3`. It must implement the documented precedence once and expose resolved mode configuration to all subcommands. Unknown keys belonging to companion applications remain ignored. Invalid values and malformed YAML produce stable diagnostics.

Configuration-directory selection must be explicit and testable for zero, one, and multiple inputs. Behaviour changes such as issue #13 remain subject to their own acceptance criteria, but the architecture must provide one shared place to implement them.

### Conversion architecture

Port the existing script event contract before replacing parsers or emitters. Each source parser produces the typed play model; each target emitter consumes it. Preserve supported edge cases, intro filtering, metadata, character tables, transitions, directions, footnotes, Unicode, and lossy-conversion warnings.

Use structured parsers or established libraries where they preserve the First Folio contract. Do not substitute ad hoc regular-expression pipelines merely to reproduce the Perl implementation language-for-language.

### Tests

Before switching a public path, capture its current accepted behaviour in Go integration tests that execute the installed-shaped `folio` binary. Tests must use fixtures and supported outputs as evidence, not source-code searches.

The Go suite must include:

- table-driven unit tests for parsers, emitters, configuration, escaping, and format detection;
- public-boundary integration tests for every existing regression-test requirement;
- golden text/Typst fixtures where exact output is contractual;
- PDF compilation plus semantic and visual evidence where layout is contractual;
- hostile-character fixtures for Typst escaping and injection resistance;
- CLI process tests for stdout, stderr, exit status, help, version, dry-run, and TTY handling;
- install-shaped tests that execute the built binary without a source checkout working directory.

Legacy tests may remain temporarily as a parity oracle during a phase, but a phase cannot remove its Perl implementation until equivalent Go tests pass independently. The final suite must not invoke Perl or project-owned shell test scripts.

### Build, install, and release

- `make build` compiles the single Go `folio` binary.
- `make install` builds before linking or installing that binary.
- `make test` runs Go tests and any explicit external-tool integration tests without shell test loops.
- `make lint` runs Go formatting/static analysis and template validation.
- `make release` obtains and stamps the version without Perl source rewriting.
- Release dependency checks cover Typst and Pandoc where the shipped feature set requires them.
- Homebrew packaging installs the single binary and declares runtime dependencies accurately.
- The executable resolves required shipped assets from an installation-safe location; it does not depend on a user-set project-root environment variable.

## Migration Sequence

1. Add characterization fixtures and Go public-boundary tests for the existing CLI, configuration, conversion, letter, manuscript, installation, and release contracts.
2. Establish the single Go command, common CLI/configuration infrastructure, installation-safe asset loading, and build/version strategy.
3. Port the stage-play document model, parsers, emitters, intro filtering, and conversion diagnostics; switch `folio convert` only after parity evidence passes.
4. Port cover-letter parsing and template-backed rendering; switch `folio letter` only after parity evidence passes.
5. Integrate the manuscript package into the single binary and remove the helper-dispatch boundary after manuscript parity passes.
6. Replace remaining shell regression and release logic with Go tests or Go tooling, then update Makefile and Homebrew packaging.
7. Remove superseded Perl modules, embedded Perl dependencies, shell test harnesses, and compatibility dispatch only after the final dependency and parity audit passes.
8. Update `ARCHITECTURE.md`, user documentation, contributor guidance, dependency declarations, and release documentation to describe the Go-only runtime.

Each switch must be a coherent, reversible commit. Do not delete the old path before its replacement has public-boundary parity evidence.

## Removal Gate

Perl and shell implementation files may be marked for removal only when:

1. Their replacement is active through the public built binary.
2. The corresponding Go unit and public-boundary integration tests pass.
3. Behavioural and PDF parity evidence has been presented for UT review.
4. No build, installation, release, Homebrew, or documentation path references them.
5. The code and test audits recommend removal with no unresolved high-severity findings.

Removal must follow the repository's recoverable deletion and issue-history rules.

## Risks and Controls

- **Silent behavioural drift:** characterize first and switch one public path at a time.
- **A rewrite that reproduces old complexity:** require typed models, focused packages, structured parsing, and file-backed templates; audit package and function boundaries at each phase.
- **PDF binary instability:** compare semantic text, page geometry, and rendered-page evidence rather than raw PDF bytes where metadata makes bytes unstable.
- **Config divergence:** one loader and typed schema for every mode, with precedence matrix tests.
- **Asset lookup failures after installation:** test the built binary outside the source-tree working directory.
- **Long-lived dual runtime:** define explicit switch/removal gates and do not add new features to superseded Perl paths during migration.

## Superseded Scope Preserved for History

The original #10 proposal was limited to moving Typst generation from Perl heredocs/string assembly into template-backed emitters while retaining Perl for data preparation. That remains a useful implementation technique, but it is superseded here because it does not resolve the split runtime, duplicated configuration/CLI concerns, or shell-heavy regression architecture. Its three original concerns -- template-backed Typst, centralized escaping, and behavioural equivalence -- are retained in AC10.6, AC10.7, and AC10.10.
