## Original issue body

# Problem

Manuscript configuration currently derives the local configuration directory from the first resolved input file. For a command such as:

```text
folio manuscript part?/ch??.md manuscript.pdf
```

the first resolved input may be `part1/ch00.md`, causing First Folio to seek local configuration under `part1/`. The invocation represents one manuscript project spanning several directories, and First Folio loads only one local configuration layer for the request. Selecting the first input directory therefore makes project-level `script.yaml` configuration undiscoverable and gives an arbitrary input file control over request-wide settings.

Local configuration discovery needs an explicit cardinality rule:

- Exactly one resolved input file: use that input file's directory.
- More than one resolved input file: use the process working directory.

The selected local directory applies to both `script.yaml` and the active style-specific file, `script-british.yaml` or `script-us.yaml`. First Folio must not inspect or merge a separate local configuration from every input directory.

# Solution Design

## Language and existing components

- Implement the change in Go within `internal/manuscript`, preserving the current Go manuscript engine.
- Keep `gopkg.in/yaml.v3`, the existing deep-merge implementation, and the existing `Config` types.
- Preserve `bin/folio` as the public command and test through that entry point.

## Configuration-directory selection

After input expansion, validation, sorting, and deduplication, select one local configuration directory from the number of resolved input paths:

1. For one resolved path, select `filepath.Dir(inputSet.Paths[0])`.
2. For more than one resolved path, obtain the process working directory with `os.Getwd()` and propagate any error with context.
3. Pass the selected directory to the existing layered configuration loader.

The rule is based on resolved, deduplicated inputs. A repeated reference to the same physical path remains one resolved input for configuration selection.

`LoadConfig` continues to load exactly one local `script.yaml` and one active local style-specific file from the selected directory. It does not walk parent directories, inspect every input directory, or merge multiple project-local configurations.

## Precedence

The change affects only selection of the local directory. Merge order remains:

1. Built-in British manuscript preset.
2. Built-in US override when selected.
3. Global `script.yaml`.
4. Global active style-specific YAML.
5. Local `script.yaml` from the selected directory.
6. Local active style-specific YAML from the selected directory.
7. CLI overrides.

## Error handling

Failure to determine the process working directory for a multi-input request must stop rendering with a contextual error. Missing optional local configuration remains valid and falls through to lower-precedence layers.

## Patterns and anti-patterns

- Keep directory selection separate from YAML parsing and merging, following CODING.md's separation of configuration from logic and preference for single-task functions.
- Use `filepath` and `os.Getwd`; do not infer directories through string manipulation.
- Do not parse YAML with regular expressions or line-oriented tools; retain `gopkg.in/yaml.v3` as required by CODING.md "Data Handling".
- Do not suppress filesystem or YAML errors; follow CODING.md "Error Suppression -- Forbidden Patterns".
- Do not add upward directory searching, per-input configuration merging, a new configuration filename, or a new CLI flag under this issue.

## Test allocation

- Add real-user regression coverage in `internal/manuscript/config_integration_test.go` or the existing manuscript integration-test location.
- Each RT executes the public `bin/folio manuscript` entry point with temporary project directories and an isolated HOME.
- Tests observe selected configuration through supported generated output rather than calling `LoadConfig` directly or inspecting source code.
- Existing focused Go tests may supplement the regression tests but do not replace public-command coverage.

## Documentation impact

- Update `docs/config.md` to define the single-input and multi-input directory rules.
- Update `ARCHITECTURE.md` so the configuration-layer description no longer says that manuscript local configuration is always beside the first source file.
- Update the README configuration summary if it continues to describe local configuration only as being beside a source file.

## Compatibility

Single-input behaviour remains unchanged. Multi-input requests that currently depend on configuration beside the first resolved input must move that request-wide configuration to the invocation directory; this is the intended correction because the first-input rule is arbitrary for a request spanning multiple source directories.
