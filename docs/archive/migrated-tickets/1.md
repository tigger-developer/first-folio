## Original issue body

## Problem

First Folio currently provides two standalone scripts (`org-play-to-markdown`, `org-play-to-pdf`) that convert from a single input format (org-mode) to two output formats. The tool needs to:

1. Support additional formats: Fountain (read and write), Markdown (read), org-mode (write).
2. Consolidate the CLI into a single `folio` command with a `convert` subcommand.
3. Route all conversions through a shared event-stream intermediate representation, so adding a format requires only a new parser or emitter — not a new conversion pair.

PDF remains write-only (Typst rendering). All text-based formats (org, Markdown, Fountain) support both reading and writing.

See [docs/formats.md](docs/formats.md) for the event stream specification and [docs/vision.md](docs/vision.md) for project goals.

Depends on #2 (config system).

## Solution Design

### Architecture: event-stream intermediate

All conversions route through a format-agnostic event stream. Each input format has an independent **parser** that emits events; each output format has an independent **emitter** that consumes them. No format-pair-specific conversion logic exists. Adding a new format means writing one parser, one emitter, or both — existing modules are not modified.

The event stream contract is the existing callback interface defined by the current `OrgPlay::Parser`. See [docs/formats.md §The Event Stream](docs/formats.md#the-event-stream) for the full event table.

```
front_matter(key, value)
act_header(title)
scene_header(title)
stage_direction(text)
character(name, direction_or_undef)
dialogue(line)
character_table_start()
character_table_row(name, desc)
character_table_end()
prop_text(text)
footnote_def(name, text)
end()
```

All parsers emit these events. All emitters consume them. PDF output goes through the Typst emitter followed by `typst compile` — a single code path for PDF rendering regardless of source format.

### Language and framework

- **Perl 5**, consistent with the existing codebase. Core modules only (no CPAN dependencies).
- **Typst** for PDF compilation (existing dependency, unchanged).

### CLI design

A single `folio` Perl script replaces `org-play-to-markdown` and `org-play-to-pdf`. Subcommand dispatch:

```
folio convert source.org target.md             # format from extensions
folio convert source.fountain target.pdf --font "Georgia"
folio convert source.org --to md               # stdout mode, format from --to
folio convert source.org --to md > play.md     # stdout redirected to file
folio convert source.org                       # stdout mode, format from default-format config
folio --help
folio --version
folio convert --help
```

**Format deduction rules:**
1. If a target file is given, format is deduced from the target extension.
2. If no target file, `--to FORMAT` specifies the output format (values: `org`, `md`, `markdown`, `fountain`, `ftn`, `pdf`).
3. If neither target file nor `--to`, the `default-format` config value is used.
4. If none of the above, error with usage hint.

**Binary output safety:** When the target format is PDF and stdout is an interactive terminal (detected via `-t STDOUT` / Perl's `-t`), `folio convert` refuses with a descriptive error:

```
Error: PDF is binary output. Refusing to write to terminal.
Use -o/--output FILE, redirect stdout, or pass --force to override.
```

`--force` bypasses the check. Piped or redirected stdout (non-TTY) proceeds without warning — this supports `folio convert play.org --to pdf | lpr` and similar pipelines.

PDF-specific flags (`--font`, `--font-size`, `--margin`, `--page`, `--indent`, `--dialogue-spacing`, `--direction-spacing`, `--[no-]direction-italic`, `--[no-]direction-center`) are accepted on `convert` when the target is PDF. They are ignored (with no error) when the target is not PDF.

The old scripts (`org-play-to-markdown`, `org-play-to-pdf`) are removed. The Makefile is updated to install `folio` to `~/.local/bin/`.

### Config file — location and precedence

**Config path:** `~/.config/first-folio/config` (new canonical location).

**Backward compatibility:** `~/.config/org-play/config` (the existing location) is loaded as a fallback if the new path does not exist.

**Precedence order (highest wins):**

| Priority | Source | Example |
|----------|--------|---------|
| 1 (highest) | CLI flags | `--font "Georgia"` |
| 2 | `~/.config/first-folio/config` | `font = Georgia` |
| 3 | `~/.config/org-play/config` | `font = Georgia` |
| 4 (lowest) | Built-in defaults | `font = New Computer Modern` |

**When both config files exist:** `~/.config/first-folio/config` is loaded; `~/.config/org-play/config` is ignored entirely. The two files are never merged — if the new config exists, it is the sole file-based config source. This avoids confusing interactions between the two files.

**Loading algorithm:**
```
1. Start with built-in defaults
2. If ~/.config/first-folio/config exists → load it, done
3. Else if ~/.config/org-play/config exists → load it, done
4. Apply CLI flags over whatever was loaded
```

**New config key:** `default-format` — sets the output format used when no target file and no `--to` flag are given.

```
# ~/.config/first-folio/config
font = New Computer Modern
font-size = 12pt
margin = 25mm
page = a4
indent = 4em
direction-italic = true
direction-center = false
default-format = md
```

Valid values for `default-format`: `org`, `md`, `fountain`, `pdf`. If unset, the absence of both target file and `--to` flag is an error.

### Parse error handling

Parsers encounter two categories of input problems:

**Hard errors (non-zero exit, conversion halts):**
- File cannot be opened or does not exist
- File is binary (not valid text)
- File has encoding errors (invalid UTF-8)
- File extension is unrecognised or unsupported as source (PDF)

These produce a descriptive error on stderr and exit non-zero immediately. No partial output is written. This follows CODING.md §Error Handling: "fail fast, fail loud, fail safe."

**Warnings (stderr message, conversion continues):**
- Ambiguous element classification (e.g. a Markdown paragraph that could be a stage direction or regular italic text)
- Non-standard formatting that the parser can recover from (e.g. character name not in ALL CAPS, missing blank line before a Fountain character element)
- Format-specific elements with no event-stream equivalent being dropped (e.g. Fountain synopses, boneyard, page breaks — see [docs/format-fountain.md §Fidelity Analysis](docs/format-fountain.md#fidelity-analysis))
- Lossy element conversion (e.g. character table being rendered as plain text in Fountain output)

Warnings are emitted to stderr in the format:
```
warning: <file>:<line>: <description>
```

Warnings do **not** cause a non-zero exit code. The exit code reflects whether conversion completed, not whether warnings were emitted.

**Per-format parsing notes:**

| Format | Hard error examples | Warning examples |
|--------|-------------------|-----------------|
| Org-mode | Binary file, encoding error | Rare — org format is well-structured via heading levels |
| Markdown | Binary file, encoding error | Character name not in bold, ambiguous italic paragraph (direction vs emphasis), table without header row |
| Fountain | Binary file, encoding error | Unclosed boneyard (`/*` without `*/`), character line with lowercase (non-forced), dropped elements (synopses, page breaks) |

**Rationale for warn-and-continue:** Markdown is the most likely to encounter ambiguous input. A strict parser that halts on every ambiguity would be unusable — many valid Markdown play documents have minor formatting inconsistencies. The parser must make a best-effort interpretation and inform the user of decisions made. The user can then fix the source or accept the interpretation.

### Parser design notes

**Fountain parser** (`Folio::Parser::Fountain`): Line-by-line state machine, same pattern as the org parser. Key detection rules per the [Fountain syntax spec](https://fountain.io/syntax):

- Title Page: `Key: Value` pairs at file start, terminated by double blank line
- Character: all-caps line preceded by blank line, not followed by blank line. Lowercase triggers warning, line treated as Action.
- Parenthetical: `(text)` after character or dialogue → mapped to character direction. Mid-dialogue parentheticals flattened to dialogue with warning (see [docs/format-fountain.md §Mid-dialogue Parentheticals](docs/format-fountain.md#mid-dialogue-parentheticals)).
- Dialogue: text following character/parenthetical
- Scene Heading: starts with INT/EXT/EST/I/E or forced with `.`
- Section (`#`, `##`, etc.): `#` → act_header, `##` → scene_header
- Action: everything else → stage_direction
- Dual dialogue (`^`): parsed, `^` marker dropped with warning, rendered as sequential dialogue (see [docs/format-fountain.md §Dual Dialogue](docs/format-fountain.md#dual-dialogue))
- Transitions: → stage_direction
- Notes: → footnote_def (auto-named)
- Synopses, boneyard, page breaks: dropped with warning

**Markdown parser** (`Folio::Parser::Markdown`): Recognises the patterns produced by the existing Markdown emitter (see [docs/format-markdown.md](docs/format-markdown.md)):

- `# Title` (H1) → front_matter(title, ...)
- `*by Author*` (italic line after H1) → front_matter(author, ...)
- `## X` (H2) → act_header
- `### X` (H3) → scene_header
- `*italic paragraph*` (standalone) → stage_direction. Warning if ambiguous (e.g. italic text that might be emphasis rather than a direction).
- `**NAME:**` or `**NAME:** *(direction)*` → character event. Warning if name is not ALL CAPS.
- Plain text after character → dialogue
- Markdown table with Character/Description columns → character_table events
- `[^name]: text` → footnote_def
- `***"TEXT"***` → prop_text

**Org parser** (`Folio::Parser::Org`): Refactored from the existing `OrgPlay::Parser` (see [docs/format-org.md](docs/format-org.md)). The org format is the most structured of the three — heading levels unambiguously encode element types, so warnings are rare.

### Emitter design notes

**Fountain emitter** (`Folio::Emitter::Fountain`): See [docs/format-fountain.md §Fidelity Analysis](docs/format-fountain.md#fidelity-analysis) for limitations.
- front_matter → Title Page block
- act_header → Section (`# Title`). Warning: invisible in formatted Fountain output.
- scene_header → forced Scene Heading (`.Title`)
- stage_direction → Action paragraph (blank line separated)
- character → Character line (ALL CAPS, blank line before, no blank line after)
- character direction → Parenthetical on next line
- dialogue → Dialogue text
- character_table → Action block with warning (no native Fountain equivalent; see [docs/format-fountain.md §Character Tables](docs/format-fountain.md#character-tables))
- prop_text → Centred text (`>TEXT<`)
- footnote_def → Note (`[[text]]`) with warning (name/numbering lost)

**Org emitter** (`Folio::Emitter::Org`):
- front_matter → `#+KEY: VALUE`
- act_header → `* Title`
- scene_header → `** Title`
- stage_direction → `*** Text`
- character → `**** NAME direction`
- dialogue → plain text
- character_table → `* CHARACTERS` + org table
- prop_text → `- *"TEXT"*`
- footnote_def → `[fn:name] text`

**Markdown emitter** (`Folio::Emitter::Markdown`): Extracted from the current `org-play-to-markdown` script. See [docs/format-markdown.md](docs/format-markdown.md) for the output schema.

**Typst/PDF emitter** (`Folio::Emitter::Typst`): Extracted from the current `org-play-to-pdf` script. Uses `Folio::TypstTemplate` for the preamble and title page, then compiles via `typst compile`.

### Patterns to follow

- **Event-driven architecture**: parsers and emitters are decoupled via the event callback interface (already established).
- **State machine parsing**: line-by-line with explicit state tracking (established in `OrgPlay::Parser`).
- **Separation of concerns**: CLI is a thin dispatcher; all logic lives in parser/emitter/config modules.
- **Fail fast**: hard errors halt immediately with descriptive messages on stderr (CODING.md §Error Handling).
- **Warnings to stderr**: recoverable issues are reported but do not halt conversion.

### Anti-patterns to avoid

- **No format-pair conversion paths** (CODING.md §Readability First): conversion must always be parser→events→emitter. No `fountain_to_markdown()` shortcut functions.
- **No string-built commands** (CODING.md §Prohibited Shell Patterns): Typst compilation uses array-form `system()`.
- **No error suppression** (CODING.md §Prohibited Anti-Patterns): unknown extensions, missing files, and unsupported conversions (PDF as source) produce clear errors on stderr and exit non-zero.
- **No inline templates** (CODING.md §Structure): Typst template stays in its own module.
- **No silent data loss** (CODING.md §Prohibited Anti-Patterns): when a format conversion drops or degrades an element, emit a warning. The user must be told what was lost.
