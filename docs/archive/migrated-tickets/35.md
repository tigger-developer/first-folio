## Original issue body

## Feature

Manuscript running headers and footers can insert semantic values through placeholders such as `[title]`, `[author]`, and `[chapter]`, but a value cannot be transformed at the point where it is inserted. Uppercasing a chapter name in the running header therefore requires changing the chapter value everywhere or adding a field-specific alias such as `chapter_upper`.

Field-specific aliases do not scale: every new transformation multiplies the placeholder vocabulary and cannot be composed. Placeholder modifiers provide a single extensible mechanism while retaining the source value and every other rendering context unchanged.

## Decision

Use pipe-delimited modifiers inside textual manuscript placeholders:

```yaml
folio:
  manuscript:
    page-header:
      format: "[title] • [chapter|upper] • [author] • [page]"
```

The initial modifier set is:

- `upper`: Unicode uppercase conversion
- `lower`: Unicode lowercase conversion

Modifiers are applied from left to right. Case modifiers apply to textual placeholders: `author`, `title`, `part`, `part-number`, `part-prefix`, `part-full`, `chapter`, `chapter-number`, `chapter-prefix`, and `chapter-full`. The numeric/contextual `page` and `total-pages` placeholders retain their existing dedicated formatting and do not accept case modifiers.

Unknown base placeholders remain literal text, including unknown tokens containing pipe-delimited text. A recognized placeholder with malformed or unsupported modifiers is a configuration error.

## Solution Design

### Language and dependencies

- Implement in Go within `internal/manuscript`.
- Continue using the standard library, the existing Typst template, and the current Go/Typst/Poppler test harness.
- Add no runtime or test dependency.

### Structured placeholder parser

Add `internal/manuscript/placeholders.go` as the owner of the manuscript placeholder mini-language. Move the existing placeholder tokenization, smart separator joining, naïve substitution, state guards, and modifier application behind this boundary.

Represent parsed tokens structurally with:

- source start and end offsets;
- the original literal token;
- base placeholder name;
- an ordered modifier list.

Use a small scanner for bracketed tokens and pipe segments. Do not extend the current regular expression into a nested modifier grammar.

The parser recognizes the grammar:

```text
[field]
[field|modifier]
[field|modifier|modifier]
```

Modifier names use lower-case ASCII letters and hyphens. A bracketed token whose recognized base name is followed by `|` is a modifier candidate even when its remaining syntax is malformed; it must reach validation rather than fall back to literal text. Modifier arguments, arbitrary functions, and user-defined expressions are outside this issue.

### Validation

Validate all eight manuscript running-page format fields during manuscript configuration validation:

- `page-header.format`
- `page-header.alt-format`
- `page-header.frontmatter-format`
- `page-header.alt-frontmatter-format`
- `page-footer.format`
- `page-footer.alt-format`
- `page-footer.frontmatter-format`
- `page-footer.alt-frontmatter-format`

Validation rules:

- unknown base placeholder: preserve the complete token literally;
- known textual placeholder plus `upper` or `lower`: accept;
- known placeholder plus unknown modifier: reject;
- empty, whitespace-containing, non-lowercase, or otherwise malformed modifier segment: reject;
- `page` or `total-pages` plus a case modifier: reject;
- explicitly empty frontmatter and alternate-frontmatter format strings: accept as blank bands.

Diagnostics name the dotted YAML field and quote the complete offending token.

### Rendering

Apply modifiers to the value expression at the point of placeholder insertion. Do not mutate metadata, manuscript blocks, or part/chapter state.

Both existing substitution paths must consume the same parsed token representation:

- consistent-separator filter/join path;
- naïve fallback path for irregular separators and single placeholders.

An empty state value remains `none` before modifier application so the existing filter/join path can remove both the value and its separator.

Case transformation uses Typst `upper` and `lower` expressions at the point of insertion for both static metadata and dynamic part/chapter state. This is Typst's locale-neutral Unicode case mapping; locale-specific casing is outside this issue. Modified metadata is escaped first and then emitted as a quoted Typst string expression before transformation; dynamic state continues to contain an escaped literal value. Unmodified metadata retains its existing emission. No source value may become executable Typst through modifier application.

### Compatibility

Unmodified recognized placeholders retain their current generated Typst and rendered PDF behaviour. Existing unknown bracket tokens remain literal, including strings that resemble a modified unknown placeholder.

The modifier grammar applies only inside manuscript page-header and page-footer format fields. It does not change source Markdown or Org, headings, TOC entries, title-page values, script placeholders, or letter substitution.

### Documentation

Update `docs/config.md` with:

- modifier grammar;
- supported textual placeholders;
- `upper` and `lower` semantics;
- left-to-right composition;
- validation behaviour;
- locale-neutral Unicode casing and expansion behaviour;
- escaping guarantees for transformed values;
- the uppercase-chapter header example.

### Patterns and anti-patterns

Follow:

- `CODING.md` §Readability First and §Code Structure: isolate the mini-language parser rather than enlarging `render.go`.
- `CODING.md` §Data Handling: parse format strings into typed tokens before transformation.
- `CODING.md` §Input Validation and §Cross-Language Escaping: validate modifier syntax before emitting Typst and retain context-specific escaping.
- Existing `internal/manuscript` configuration normalization, template rendering, temporary-directory, and PDF-inspection patterns.

Avoid:

- aliases such as `chapter_upper`;
- a field-by-modifier switch-product;
- chained regular expressions or ad hoc string replacement;
- arbitrary Typst or Go expressions from YAML;
- mutation of canonical metadata or semantic heading state;
- duplicated placeholder logic between header/footer or smart/naïve rendering paths;
- new dependencies or shell-based test orchestration.
