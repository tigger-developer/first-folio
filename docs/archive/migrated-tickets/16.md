## Original issue body

# Parity-aware book layout, Roman-numeral frontmatter, and numbering resets

## Problem

Issue #15 established the underlying primitives for book-layout manuscripts (page-pair alignment, enforce-right / enforce-left, gutter, skip-header / skip-footer). During the #15 review the physical-vs-display page counter split was addressed inline via BYPASS-GATE-7, so the fundamental parity math is now correct. Issue #24 subsequently added the frontmatter/body distinction for header and footer format strings. Issue #21 delivers the copyright frontmatter page itself.

This ticket collects the remaining parity/numbering/flushness work that was parked at the end of #15 or flagged as future work during those tickets' discussions.

## In scope

### 1. Roman-numeral frontmatter numbering

Traditional book design numbers the frontmatter (title, copyright, TOC, dedication, foreword, preface, introduction) with lowercase Roman numerals (`i`, `ii`, `iii`), then restarts at `1` (arabic) for the body starting at the first part or chapter. Currently first-folio hides the page counter entirely on the frontmatter via `numbering: none`.

**Config surface (mirroring the existing `part.number-format` / `chapter.number-format` convention which uses `1` / `I` / `i` values):**

```yaml
folio:
  manuscript:
    page-numbering:
      frontmatter-format: "i"   # "1" | "I" | "i"; default "1" (unchanged from today)
      body-format: "1"           # "1" | "I" | "i"; default "1"
      body-reset: first-part-or-chapter   # default; also "never" (continuous through frontmatter)
```

The `[page]` placeholder in `page-header.format` / `page-footer.format` (and their `frontmatter-format` / `alt-frontmatter-format` counterparts from #24) resolves to the counter in the appropriate style based on which region the page is in.

The frontmatter/body boundary is already marked by the `folio-is-body` state (added in #24). This ticket wires the numbering-style selection to that state.

### 2. Chapter-number reset as a config toggle

Chapter numbering currently resets to 1 at each new part. This is hardcoded in the parser (`chapterNumber = 0` on every new H1). Expose it as a config toggle:

```yaml
folio:
  manuscript:
    chapter:
      number-reset: per-part      # default; matches current hardcoded behaviour
      # other values: "never" (chapters number continuously across parts)
```

Same offset-integer pattern as the page display counter (introduced in #15 BYPASS-GATE-7). Introduce `folio-chapter-offset` state seeded at part boundaries when `number-reset: per-part`, or seeded once at document top when `never`. Chapter display number = physical chapter counter − chapter offset.

### 3. Enforce-right / enforce-left as first-class parity primitives

Currently implemented as values of `blank-page-before` / `blank-page-after` (see AC15.11). They work correctly now that parity math uses the physical counter. This ticket brings them out of the "amended AC" back into a first-class definition and expands the accepted usage:

- Verify enforce-right for `part`, `chapter`, and `toc` produces the correct blank-verso insertion in every combination (single-part multi-chapter; multi-part; enforce-right on TOC combined with enforce-right on part combined with enforce-right on chapter; short chapters vs long chapters).
- Add PDF-level regression tests that compile the Typst and inspect the actual page count and per-page content via `pdfinfo` / `pdftotext -layout`.
- Add a UT for a facing-page rendered PDF that visibly demonstrates parts and chapters landing on recto.

### 4. Outer-edge running-head flushness

The running header on chapter body pages currently lives inside the content area (page − inside − outside margins). Outer-edge convention places the header text against the outer margin of the trimmed page, which is slightly further out than the content area's edge. This is a small visual polish (few millimetres) but worth doing for book renderings.

### 5. Frontmatter and body counter separation

The BYPASS-GATE-7 fix added the offset state approach for the page counter. It works but is single-use (one boundary between frontmatter and body). If we later want more boundaries (backmatter → new numbering; different Roman-numeral runs for foreword vs preface), the state pattern needs to become a proper numbering-stack. Design this ticket's implementation with that extensibility in mind rather than baking in the single-boundary assumption.

## Out of scope

- Copyright block (delivered by issue #21; item 3 in the original #16 body has been removed here)
- Backmatter numbering (endnote / index / bibliography) — separate follow-up
- Marginalia, drop caps, opening-page ornaments — separate follow-up
- Print-shop bleed / crop marks — separate follow-up

## Design principles

- **Reuse the existing convention.** Number formats use `1` / `I` / `i` (same as `part.number-format` / `chapter.number-format`). Do not invent `roman-lower` / `roman-upper` strings.
- **Reuse the existing state.** `folio-is-body` from #24 marks the frontmatter/body boundary. `folio-page-offset` from BYPASS-GATE-7 handles the page-counter display shift.
- **Extensible offset pattern.** Both page-number and chapter-number use the same "physical counter − offset" pattern. Backmatter can extend it without schema round-trip.
- **Preserve backwards compatibility.** Every default matches current behaviour byte-for-byte (`page-numbering.body-reset: first-part-or-chapter`, `chapter.number-reset: per-part`, `frontmatter-format: "1"`).
