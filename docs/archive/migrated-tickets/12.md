## Original issue body

## Problem

Cover-letter generation preserves org inline code/verbatim markup literally in the rendered letter body. An org letter body containing `=inline code=` emits `=inline code=` into the generated Typst source instead of rendering the marked text in a monospace style.

Observed reproduction on 2026-07-10:

- Source body: `This sentence has =inline code= in it.`
- Command: `TMPDIR="$PWD/.agent/tmp/letter-code-repro/tmp" FOLIO_KEEP_TYPST=1 bin/folio letter .agent/tmp/letter-code-repro/repro.org --dir .agent/tmp/letter-code-repro --prefix repro2`
- Generated Typst body: `This sentence has =inline code= in it.`

## Violated Acceptance Criteria

- AC6.6 (legacy, issue #6): Org markup (bold, italic, underline) renders in letter body.

Inline org code/verbatim markup is part of org body markup and should render semantically, matching Markdown inline code behaviour where applicable.

## Solution

Update the cover-letter body markup conversion so org inline code/verbatim spans written as `=text=` render as monospace Typst text rather than literal equals signs.

The implementation should preserve existing bold, italic, and underline behaviour. It should use the existing letter body escaping path and avoid changing the cover-letter source contract beyond adding the missing inline code handling.

## Regression Tests

Add regression coverage through the user-facing `folio letter` command:

- RT-12.1: An org cover-letter body containing `=inline code=` renders generated Typst with monospace text and without literal equals delimiters.
- RT-12.2: Existing org bold, italic, and underline cover-letter markup still renders semantically after inline code support is added.

No new AC table is added because this bug references legacy AC6.6 from issue #6.
