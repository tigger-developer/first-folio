## Original issue body

## Problem

First Folio currently uses a flat `key = value` config file at `~/.config/org-script/config`, loaded only by `org-play-to-pdf`. This has several limitations:

1. **No shared config with other tools.** The play script converter [yapper](https://github.com/tigger04/yapper) (TTS rendering) also processes play scripts and needs overlapping metadata (title, author, subtitle) and rendering options. Each tool maintains its own config independently.
2. **No per-project config.** A `script.yaml` alongside the source file allows per-project settings without modifying the global config — and can be version-controlled with the play.
3. **Flat format.** The current `key = value` format cannot represent namespaced settings. YAML supports nested keys, allowing each tool to own its own namespace (`folio:`, etc.) while sharing top-level metadata and rendering options.
4. **Wrong location.** The config path `~/.config/org-script/` reflects the old project name. The canonical location should be `~/.config/first-folio/`.

This issue establishes the config system that issue #1 depends on. It should be implemented first.

## Config file schema

A shared `script.yaml` authored and maintained by the user (or by other tools). **First Folio only reads config files — it never creates, modifies, or writes to them.** The YAML file is an input to the application, not an output.

Each tool reads shared top-level keys plus its own namespace, ignoring everything else.

```yaml
# Shared metadata — authoritative project-level values
# These override any title/author/subtitle found in the source document
title: "About Time"
subtitle: "A Play in Two Acts"
author: "Tadhg Paul"
draft-date: "2026-04-26"

# Shared rendering options (read by both folio and yapper)
render-stage-directions: true
render-intro: true
render-footnotes: true
render-character-table: true

# Yapper-specific (silently ignored by folio)
auto-assign-voices: true
character-voices:
  KEVIN: af_alloy
  NESSA: af_heart
  CÁIT: bf_isabella
narrator-voice: bf_alice
dialogue-speed: 1.0
speech-substitution:
  Cáit: Kawch

# First Folio PDF rendering (silently ignored by yapper)
folio:
  font: "New Computer Modern"
  font-size: 12pt
  margin: 25mm
  page: a4
  indent: 4em
  dialogue-spacing: 1.6em
  direction-spacing: 1.6em
  direction-italic: true
  direction-center: false
  default-format: md
```

### Key categories

| Category | Keys | Read by |
|----------|------|---------|
| Shared metadata | `title`, `subtitle`, `author`, `draft-date` | Both folio and yapper |
| Shared rendering | `render-stage-directions`, `render-intro`, `render-footnotes`, `render-character-table` | Both folio and yapper |
| First Folio specific | Everything under `folio:` | folio only |
| Yapper specific | `character-voices`, `narrator-voice`, `dialogue-speed`, `speech-substitution`, etc. | yapper only |

First Folio reads: `title`, `subtitle`, `author`, `draft-date`, `render-stage-directions`, `render-intro`, `render-footnotes`, `render-character-table`, and everything under `folio:`. All other top-level keys are silently ignored.

## Config precedence — layered merge

**All** config sources are read and merged in precedence order. Each layer overrides individual keys from the layers below — not the entire config. This allows a global `script.yaml` to set defaults (e.g. font, page size) while a local `script.yaml` overrides only what differs for a specific project (e.g. title, author).

| Priority | Source | Notes |
|----------|--------|-------|
| 1 (highest) | CLI flags | `--font "Georgia"` |
| 2 | Local `script.yaml` | In the same directory as the source file (read-only) |
| 3 | Global `~/.config/first-folio/script.yaml` | User-wide defaults (read-only) |
| 4 (lowest) | Built-in defaults | Hardcoded in the application |

**Example:** Global config sets `folio.font: "New Computer Modern"` and `folio.page: a4`. Local config sets `folio.font: "Georgia"` only. Result: font is Georgia, page is a4.

The deprecated flat config at `~/.config/org-script/config` is no longer read. This is a clean break — the old format is not supported.

First Folio never creates, modifies, or writes to any config file.

## Solution Design

### Language and framework

- **Perl 5**, consistent with the existing codebase. Core modules only — no CPAN dependencies.
- YAML parsing uses a purpose-built minimal parser for the config subset (scalars, one-level-deep maps, comments). Full YAML spec support is not needed and would require CPAN.

### Module structure

```
lib/Folio/Config.pm          # Config loading, merging, and access
lib/Folio/Config/Yaml.pm     # Minimal YAML subset parser (read-only)
lib/Folio/Config/Legacy.pm   # REMOVED — no legacy config support
```

Only two new files. `Folio::Config` is the public interface; `Folio::Config::Yaml` is the parser. No legacy reader — `~/.config/org-script/config` is dead.

### Folio::Config — public interface

```perl
my $config = Folio::Config->load(
    source_dir => dirname($input_file),   # for local script.yaml lookup
    cli        => \%cli_opts,             # CLI flag overrides
);

# Access resolved values
my $font  = $config->get('folio.font');           # "New Computer Modern"
my $title = $config->get('title');                 # shared metadata
my $render_dirs = $config->get('render-stage-directions');  # shared rendering
```

`load()` is the only entry point. It reads all sources, merges them, and returns a frozen config object. **No writing occurs. No config files are created or modified.**

### Merge algorithm

```
1. Start with built-in defaults (hardcoded hash)
2. If ~/.config/first-folio/script.yaml exists → read it, merge over defaults
3. If <source_dir>/script.yaml exists → read it, merge over result of step 2
4. Merge CLI flags over result of step 3
```

**Merge semantics:** shallow per-key override. For top-level scalars (`title`, `author`, `render-stage-directions`, etc.), the higher-priority value replaces the lower. For the `folio:` map, individual keys within the map are merged — a local config that sets only `folio.font` does not erase `folio.page` from the global config.

```
# Global script.yaml
folio:
  font: "New Computer Modern"
  page: a4
  margin: 25mm

# Local script.yaml
title: "About Time"
folio:
  font: "Georgia"

# Merged result:
title: "About Time"           # from local
folio:
  font: "Georgia"             # local overrides global
  page: a4                    # global survives (not overridden)
  margin: 25mm                # global survives (not overridden)
```

### Folio::Config::Yaml — minimal parser

Read-only parser for the YAML subset used by config files. Handles:

- **Scalars:** `key: value`, `key: "quoted value"`, `key: 'single quoted'`
- **One-level maps:** a key with no inline value followed by indented `key: value` lines
- **Comments:** lines starting with `#` (including inline `# comment` after a value)
- **Blank lines:** ignored
- **Boolean normalisation:** `true`/`false`/`yes`/`no`/`on`/`off` → 1/0

Does **not** handle: multi-line strings, anchors/aliases, flow style (`{}`/`[]`), multi-document (`---`), nested maps beyond one level, sequences.

Returns a two-level hash: `{ key => value, folio => { font => "...", page => "..." } }`.

**Error handling:** Malformed YAML (e.g. unmatched quotes, invalid indentation, tabs where spaces expected) produces a descriptive error on stderr with the file path and line number, then exits non-zero. This follows CODING.md §Error Handling: "fail fast, fail loud, fail safe."

### Integration with existing scripts

The new config module replaces `_load_config()` in `org-play-to-pdf` (lines 313–351). The existing script's flow changes from:

```
hardcoded defaults → _load_config() → GetOptions
```

to:

```
Folio::Config->load(source_dir => ..., cli => ...) → use resolved values
```

The hardcoded defaults move into `Folio::Config` as the built-in defaults hash. `GetOptions` still runs first to capture CLI flags, which are passed to `load()`.

`org-play-to-markdown` gains config support for the first time — it currently has no config loading. After this change, shared metadata (`title`, `subtitle`, `author`) and shared rendering keys (`render-stage-directions`, etc.) apply to Markdown output too.

### Front matter override (AC2.5)

Config metadata overrides source document metadata. The override happens **after** parsing, not during. The parser emits `front_matter` events from the source document as usual. After parsing completes, the CLI applies config overrides:

```perl
# After parsing, before emitting output:
$front_matter{title}    = $config->get('title')     if defined $config->get('title');
$front_matter{subtitle} = $config->get('subtitle')  if defined $config->get('subtitle');
$front_matter{author}   = $config->get('author')    if defined $config->get('author');
$front_matter{'draft-date'} = $config->get('draft-date') if defined $config->get('draft-date');
```

This preserves the parser's purity (it reads the document, nothing else) and keeps the override logic in the CLI layer where it belongs.

### Rendering key behaviour (AC2.3)

The `render-*` keys control whether certain event types are passed through to the emitter:

| Key | Default | Effect when `false` |
|-----|---------|-------------------|
| `render-stage-directions` | `true` | `stage_direction` events are suppressed |
| `render-intro` | `true` | Title page / opening block is suppressed |
| `render-footnotes` | `true` | `footnote_def` events are suppressed; inline references are left as-is or stripped |
| `render-character-table` | `true` | `character_table_*` events are suppressed |

Suppression happens in the CLI dispatch layer (between parser and emitter), not inside the parser or emitter. The parser always emits all events; the emitter always handles all events it receives. The CLI filters the event stream based on config.

### draft-date rendering (AC2.5, RT-2.15)

`draft-date` is a new field not currently rendered. The Typst title page template (`OrgPlay::TypstTemplate::title_page`) needs a `draft_date` parameter. When present, it renders below the author line:

```typst
#v(0.5em)
#text(size: 1em)[Draft: 2026-04-26]
```

### Patterns to follow

- **Read-only config**: the module reads files and returns data. It never opens a file for writing. No `open(... '>')` anywhere in the config code. (CODING.md §File Operations — but inverted: we don't even need atomic writes because we don't write.)
- **Fail fast on bad YAML**: descriptive error with file path and line number, exit non-zero (CODING.md §Error Handling).
- **Separation of concerns**: the YAML parser returns a hash; the Config module handles merging and access; the CLI handles integration. Each layer does one thing.
- **Explicit state, no globals**: the config object is passed explicitly, not stored in a package global. Functions that need config receive it as a parameter (CODING.md §Prohibited Anti-Patterns: "Global variables for state — hidden dependencies, testing nightmare").

### Anti-patterns to avoid

- **No writing to config files** — this is the core constraint. The module is read-only. Not even a "helpful" config initialisation or migration feature.
- **No error suppression** (CODING.md §Prohibited Anti-Patterns): malformed YAML is a hard error, not a silent fallback to defaults.
- **No `eval` for YAML parsing** (CODING.md §Prohibited Shell Patterns, generalised): the YAML parser uses regex and state machine logic, not string evaluation.
- **No deep merge beyond one level**: the `folio:` map is merged one level deep. If deeper nesting is ever needed, the schema must be extended deliberately — not by adding recursive merge logic that silently handles arbitrary depth.
