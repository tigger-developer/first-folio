* Environment

- Platform :: macOS, Darwin arm64.
- Toolchain :: Go 1.26.3, Typst 0.14.2, Pandoc 3.9.0.2, Poppler =pdftotext=
  26.09.0.
- Font isolation :: The PDF regressions compile with =--ignore-system-fonts= and
  a fixture configuration supplying DejaVu Sans Mono, a *single-width family*.
  That family is what makes the defect observable: face selection cannot change
  its width, so any width change must come from proportional scaling.

* Regression tests

** GREEN RT043.1 - Proportional block stretch :testdef:
:PROPERTIES:
:REVISION: 92d5826 - apply configured monospace stretch to code blocks
:COMMAND: go test ./internal/manuscript -run TestRT043_1ProportionalBlockStretch
:EVIDENCE: Eight cases pass across Markdown and Org at 150%, 200% and 50%, measured against each format's 100% rendering. See the dated runs below.
:END:

*** Run 2026-09-17, before the change

Executed at =40de99c= plus the new test file, with the template unchanged.
Observed the intended behavioural failure: code width was *identical at every
configured percentage*, so the configured stretch had no effect.

#+begin_example
block_stretch_test.go:75: codeA width 54.185pt, want 81.277pt at 150%
block_stretch_test.go:75: codeA width 54.185pt, want 108.369pt at 200%
block_stretch_test.go:75: codeA width 54.185pt, want 27.092pt at 50%
block_stretch_test.go:89: codeC offset from the block edge 21.674pt, want 32.511pt at 150%
#+end_example

The same failures appeared for Org input, confirming the defect was not
specific to one reader.

*** Run 2026-09-17, after the change

Executed at =92d5826=. All eight subtests pass: measured widths, offsets from
the block edge, unchanged vertical bounds, retained line structure and
unchanged surrounding prose.

#+begin_example
ok  github.com/tigger-developer/first-folio/internal/manuscript
#+end_example

* User tests

** GREEN UT043.1 - Compare rendered code-block and inline widths :testdef:
:PROPERTIES:
:REVISION: 92d5826 - apply configured monospace stretch to code blocks
:EVIDENCE: Approved 2026-09-18. Four rendered manuscripts at 100%, 150%, 200% and 50%, each carrying a fenced code block and paragraph inline monospace on one page, were accepted as showing the same scaling in both places.
:END:

- Method :: User validation.
- Observed outcome :: Code blocks and paragraph inline monospace render at the
  same configured stretch as *one consistent typographic treatment*. The earlier
  pending acceptance recorded below is superseded by this result.

*** Prepared measurement 2026-09-17

Revision =92d5826=. A chapter containing paragraph inline monospace and a
fenced block with a four-space indented line, rendered at 100% and 200% with
=folio.manuscript.mono.font.stretch= as the only difference.

| Marker                  | 100%     | 200%     | Ratio |
|-------------------------+----------+----------+-------|
| =def= width             | 19.200pt | 38.400pt | 2.00  |
| =align(a,= edge offset  | 25.600pt | 51.200pt | 2.00  |
| =return= edge offset    | 25.600pt | 51.200pt | 2.00  |
| =inline_code= width     | 70.400pt | 140.800pt | 2.00 |

The block's left edge stayed at 56.693pt and both code lines held their
vertical positions, 349.193pt and 364.193pt. The four-space indent scaled with
the glyphs, so the column grid remained aligned. Paragraph inline monospace
scaled by the same ratio, which is the *equivalence the change was authorized
to produce*.
