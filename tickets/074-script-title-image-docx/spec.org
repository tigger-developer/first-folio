* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome

- DOCX conversion applies W073's *script title-page image contract* while keeping title metadata editable.

** Before

- Native DOCX title pages contain text only and cannot represent configured background or inset artwork.

** After

- Background and inset images are *embedded in the DOCX package* with proportional geometry.
- Overlay uses editable title text over localized blur and wash regions; inset-only dodge places editable metadata above and below the centred image.
- An inset can reuse W079's *prepared blurred JPEG or exact solid-colour backdrop* behind the sharp image and editable metadata.

** Changes

- The native DOCX writer projects the shared title-image plan into page-anchored OOXML drawings and editable text regions.
- The projection consumes the *current resolved source configuration*, including literal title percentages, exact title-to-subtitle spacing, post-placement dodge padding and the anchored bottom-centre author slot.

** Unchanged

- The W073 YAML contract, source-relative path rule, non-title content, manuscripts, letters and no-image DOCX route *remain unchanged*.

** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:

- Missing or invalid assets and unsupported combinations *fail atomically*; office-reader repair prompts are not acceptable output.

** Decisions

- DOCX adds *no format-specific configuration* and does not rasterize title metadata into the image.

** Next step

- Definition review, then operator sign-off as described in [[#delivery-handoff][Delivery Handoff]].

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

After W073, the public cover-image configuration would apply to PDF only. DOCX is a supported editable script output, so silently omitting the configured title-page image or flattening the title metadata would make the conversion contract inconsistent.

** Outcome

=folio convert= produces a self-contained DOCX whose dedicated script title page follows W073 geometry and placement semantics and remains usable in a Word-compatible editor.

** Scope

*** In scope

- Dedicated script title pages produced by =folio convert= to DOCX.
- Background and inset modes, overlay and inset-only dodge placement, independent image and wash treatments, blur and equal-sided padding as defined by W073.
- W079 image and solid inset backdrops, reusing the conversion-scoped prepared JPEG and resolved wash treatment.
- Embedded PNG/JPEG image parts, page-relative positioning, cropping and editable title metadata.
- The same YAML cascade used by the PDF renderer, including Markdown YAML and dotted Org source frontmatter.

*** Out of scope

- New YAML keys or altered W073 semantics.
- PDF, ODT, manuscripts, letters, compact script titles and source-body images.
- Pixel-identical pagination or font metrics across Word-compatible editors.

*** Unchanged

- The script parser, YAML cascade, image path base, later-page body content, native footnotes/comments and existing no-image title-page output.

- Project profile :: [[file:../../.sdlc/project.yaml][=.sdlc/project.yaml=]].
- Product authority :: [[file:../073-script-title-image-pdf/spec.org][W073 shared script title-image contract]] and [[file:../../docs/format-docx.md][DOCX format contract]].
- Architecture authority :: [[file:../../docs/ARCHITECTURE.md][Project architecture]].
- Current implementation fact :: [[file:../../internal/office/docx_pages.go][=internal/office/docx_pages.go=]] builds native DOCX title pages and =internal/office= owns package serialization.
- Following work :: [[file:../075-script-title-image-odt/spec.org][W075 - ODT title-page images]].

** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:

- W073's approved shared configuration and title-image plan must be delivered before W074 implementation begins.
- The output must be self-contained and open without an external image path, network fetch, repair prompt or postprocessor.
- Title, subtitle, author, date and version remain editable text and use their configured typography.
- Office-reader layout variation is permitted only within documented physical tolerances; mode, ordering, non-overlap and aspect ratio are not approximations.

** Decisions

- W074 consumes top-level =folio.cover-image= exactly as defined by W073 and introduces no DOCX override.
- W074 consumes W079's =folio.cover-image.backdrop= block without regenerating the prepared blurred JPEG or maintaining a DOCX-specific treatment model.
- Background drawings are anchored to the physical page, behind text, and cover the configured page rectangle using W073's centred crop.
- Insets are centred on the physical page with explicit physical extents. Overlay uses one editable primary region for title/subtitle/author and separate populated date and version regions, never full-width wash bands; dodge text remains in editable positioned regions above and below the image.

** Unresolved blockers

- None.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Relevant components :: The application owns W073/W079 validation, source-relative resolution and prepared image variants, including W079's JPEG backdrop derivative; the native DOCX writer owns page geometry, editable text, drawings, media and relationships.
- Ownership boundary :: First Folio creates the complete OOXML package. Word-compatible editors own final layout and editing but must not be required to repair or fetch content.
- Existing pattern :: Extend the native writer's title-page and package-part builders rather than adding Pandoc or a post-processing executable.

** High-level design

*** Components and responsibilities

- The application passes an immutable =office.ScriptCover= projection containing resolved geometry and bounded selected/prepared asset bytes into the DOCX writer. It includes requested Superscale output, documented original-image fallback and any prepared backdrop JPEG without rerunning external processing.
- The package layer embeds original/normalized and blurred image parts, registers content types and relationships, and allocates identifiers through existing package mechanisms.
- The title-page writer creates page-anchored image layers and positioned editable text regions in the plan's order.

*** Reuse, shared behaviour and variation

- Shared operation :: Asset resolution, validation, proportional image geometry, independent image/wash treatment and backdrop preparation remain in the application-owned W073/W079 pipeline. The DOCX adapter maps the resolved values into office-native geometry without changing their meaning.
- Variation :: DOCX maps physical units to EMUs and uses OOXML drawings/text containers while preserving shared semantics.

*** Boundaries and dependencies

- Add no new runtime process or network dependency. Use native OOXML supported by the project's target Word-compatible editors.
- Prepared assets are package-local; relationships use internal targets only.

*** Flow

1. Public conversion loads the established configuration cascade, runs the existing W073/W079 preparation pipeline once and adapts its result to =office.ScriptCover=.
2. The DOCX writer embeds required sharp, treatment and backdrop image variants and constructs title-page visual layers behind editable text.
3. Existing body and section generation follows, then the complete package is validated and atomically published.

*** Essential mechanisms

- A background drawing is anchored at page origin behind document text with page-sized extents and the plan's centred source crop.
- An image backdrop reuses W079's prepared page-sized JPEG as the lowest full-page drawing; a solid backdrop uses one page-sized native DrawingML fill. The resolved wash is a separate full-page shape above the backdrop and below the sharp inset and text.
- An inset drawing uses explicit page-centred position and longest-axis extents.
- Overlay regions use positioned editable text containers. Their background layer clips the aligned blurred image variant to the padded region, adds the independently configured lightening or darkening wash, then places its defined contrasting text above it.
- Dodge uses separate upper and lower text regions around the page-centred inset. Region-relative =center= and =third= coordinates come from the shared plan rather than Word paragraph spacing heuristics.
- Literal percentages, exact subtitle gaps, post-placement dodge padding and bottom-centre author placement are resolved into page-relative office geometry rather than collapsed to the writer's existing fixed paragraph-spacing aliases.

*** Interfaces and configuration

- Public interface :: No new user-facing interface; consume the established top-level =folio.cover-image= and title-page configuration.
- Internal interface :: Add an optional =office.ScriptCover= value to the native script export boundary. It carries only resolved scalar geometry/treatment values and bounded asset bytes with their media types; =internal/office= does not import =internal/app=, resolve source paths or invoke Superscale.
- Compatibility :: The writer selects the image route only when =office.ScriptCover= is present. Existing title paragraphs remain the no-image route.

*** Data and state

- Image parts, including the prepared backdrop JPEG, are embedded under =word/media= with package relationships. The conversion-scoped =office.ScriptCover= owns copied bytes only for package construction; no external link, source path or cache survives conversion.
- Source files and W073 prepared temporary assets remain read-only and conversion-scoped.

*** Failure behaviour

- Missing assets, invalid plan geometry, duplicate identifiers or package validation failure abort before target replacement. A recognized backdrop is not rejected as an unsupported DOCX field.
- Errors retain W073 field/path context where the failure originates and otherwise identify the DOCX packaging boundary.

*** Simplicity and proportionality

- One native adapter reuses the existing DOCX writer and application preparation pipeline. It avoids a second configuration model, duplicate blur processing, an external postprocessor and rasterized title text.

** Design decisions and verification

*** Keep title metadata editable

- Decision :: Use native editable text containers above image/treatment layers; do not bake metadata into PNG/JPEG assets.
- Verification :: [[#rt-074-1][RT074.1 - Native DOCX package represents the shared image plan]] inspects text nodes and [[#ut-074-1][UT074.1 - DOCX title images remain editable and stable]] verifies editing and round-trip behaviour.

*** Use physical page anchoring

- Decision :: Anchor image and overlay geometry to the page rather than to flowing body paragraphs.
- Rationale :: Flow anchoring cannot reliably express full-page cover crop or region-relative dodge placement.
- Verification :: [[#at-074-1][AT074.1 - Public DOCX conversion preserves title-image semantics]] measures rendered geometry and non-overlap.

** Routine details left to implementation

- OOXML element helper names, media filenames and relationship numbering may follow existing package conventions.
- Helper structure and raster sampling details may follow the existing isolated-profile office-render test conventions; the =2mm= geometry and =1%= aspect-ratio tolerances in AT074.1 remain fixed.

** Architecture impact

*** Security impact

- Threat boundary :: Unchanged from W073's local untrusted image input; DOCX adds a ZIP/XML serialization boundary.
- Data and secrets :: Only requested image bytes and derived local variants are embedded. No source path or unrelated file content is added to the package.
- Access :: No additional file, process, network or privilege access beyond W073 asset loading and target publication.
- Conclusion :: Reuse W073 resource bounds, escape XML, allocate collision-free parts and validate internal relationships before atomic publication.

*** Other relevant qualities

- Interoperability :: Native, conforming OOXML and editor round-trip validation are required; proprietary external links are excluded.
- Accessibility :: Metadata remains selectable text with contrast treatment; background artwork is decorative unless a later accessibility ticket adds alternative text policy.
- Maintainability :: The DOCX adapter consumes shared geometry rather than recalculating policy.
