* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome

- *Manuscripts and letters export to editable DOCX and ODT* with their existing typography and document features.

** Before

- *Manuscripts produce Typst or PDF*; *letters produce PDF* per recipient.
- Script conversion already has native DOCX and configured Pandoc ODT writers.

** After

- *Manuscript target extensions select DOCX or ODT*; *letter --format selects pdf, docx or odt*.
- *Letters retain one file per recipient*, filtering, substitution and naming.
- *DOCX and ODT follow the same YAML configuration cascade as their mode's PDF renderer*, controlling every applicable feature, including manuscript contents, copyright, numbering and running matter.
- Cascade, lowest to highest :: British built-in preset; selected style preset; global =script.yaml=; global style-specific YAML; first resolved Markdown manuscript input's =folio:= and =render:= frontmatter mappings (manuscripts only); local =script.yaml=; local style-specific YAML; CLI overrides.
- *Fonts use the existing embedding policy*; *pagination may differ* between reading applications and PDF.
- *Labelled reference fixtures and named user tests demonstrate every supported YAML feature*, with explicit expected values and a key-to-test checklist.
- *Automated office-to-PDF measurements precede user review*; page PNGs support visual inspection without requiring pixel-identical pagination.
- *Novel-scale Markdown and Org produce usable DOCX and ODT*: retained conversion regressions, a ticket-scoped automated rendering test and human editing checks cover all four combinations.

** Changes

- *Extend the native parser used by folio convert* for manuscript and letter office output, retaining distinct mode semantics and extending the existing exporters.
- *DOCX uses no Pandoc at any stage*, including source parsing, canonicalization, metadata, dry-run and reference discovery.
- *ODT alone uses Pandoc in the office route*: native parsed content becomes JSON for the configured ODT writer, followed by native layout adjustment and font embedding.

- *Office output is bounded and published atomically per file*; office-only collision preflight prevents two letters from replacing each other. PDF letter path behaviour is unchanged.

** Unchanged

- *PDF/Typst and script conversion behaviour remain unchanged*; script DOCX retains its native writer.
- *Source formats, configuration precedence and font discovery remain unchanged*; no downloads, cloud service or office input support is added.

** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:

- *Invalid input or malformed output fails* without replacing the affected destination. *Unavailable Pandoc blocks ODT, never DOCX*.

- *Duplicate letter targets fail before publication*. Later publication failure reports the files already written; a letter batch is not a transaction.
- *Missing or restricted fonts warn* under the existing policy; *other feature loss is not silently accepted*.
- *Contents and page fields may need updating in the editor*; no fixed PDF page-number cache is substituted.

** Decisions

- *All existing applicable features are required*, not the smaller script-export subset. Unsupported mappings require a scope decision before delivery can claim conformance.
- *Internal definition review applies* under the standing policy. This parser correction requires renewed operator sign-off; earlier reviews remain historical evidence.

** Problem and outcome

Manuscript and letter users need *editable office documents without rebuilding their formatting manually*. Export must preserve the existing mode's content and resolved layout settings. Different pagination is acceptable; replacing configured features with writer defaults is not.

** Scope

- Included :: DOCX and ODT output for existing Markdown/Org manuscripts and Org letters; full applicable configuration, embedded fonts, public CLI/help, output safety and regression protection.
- Excluded :: Office input, new source syntax, source images, new YAML roles, a universal document model, replacing script writers, changing PDF layout, releases and installation.
- Preserved :: Existing defaults, metadata precedence, source discovery, private-section handling, recipient semantics and the accepted =verbatim= workaround for literal slashes in letters.

** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:

- Runtime :: *DOCX is native from source parsing through publication for all three modes*. No DOCX path may invoke or require Pandoc, including metadata, canonicalization, dry-run, version/API probes or references. Office source parsing extends the native parser used by =folio convert=. *ODT retains the configured Pandoc writer*, receiving JSON projected from native content. Typst and desktop office applications are not runtime dependencies of office output; existing PDF/Typst dependencies are unchanged.

- Fidelity :: Preserve *all applicable YAML typography and document features*. Native length rounding and editor-dependent line/page breaks are acceptable. Hyphenation positions can differ while the configured policy remains effective. The operator approved one additional ODT exception on 2026-10-16: start a new page at the frontmatter/body boundary when the page-number format changes. Preserve configured displayed numbering and physical page-side rules at that boundary; PDF behaviour is unchanged. The operator subsequently approved extending that ODT new-page exception to a requested body-number reset or a change in running-band page-field structure, and accepted the weight mapping documented below. The approved DOCX opening-page exception is defined below.
- DOCX opening-page exception :: Approved 2026-10-17. Special first-page handling may use the odd variant of a retained header/footer on an even physical opening page. Suppression, displayed page counters and subsequent-page parity remain required. Ordinary chapter/part openings retaining both bands are unaffected. The observed ODT parity case passes; this exception does not weaken ODT parity requirements.
- Fonts :: The existing permission, discovery and supported-font-file policy remains applicable. Referenced unavailable or non-embeddable faces warn and retain their family references. This exception does not permit dropping configured size, style, stretch or tracking. The approved weight mapping is regular below 600 and bold from 600 upwards in DOCX; ODT retains standard weights in steps of 100 and uses that same binary fallback for intermediate values. Embedding retains the existing regular/bold/italic face policy; numeric ODT weights do not guarantee a distinct embedded face.
- Review route :: External composite definition review covers specification, design and test definitions. The earlier session exception allowing self-review alone is superseded for this definition on 2026-10-16. Only the harness creates or updates [[file:audits.yaml][Independent review evidence]]. From 2026-10-18, the standing internal-only policy supersedes that invocation route for remaining reviews; record the delivery review in =internal-review.md= and preserve historical harness evidence.
- Delivery admission :: Requires explicit sign-off of this document. The acknowledgements establishing scope do not approve an unseen solution design.
- Test categories :: *RT* denotes retained automated regression, *AT* ticket-scoped automated RED/GREEN verification outside the regression pack, *OT* genuinely one-off verification, and *UT* human-dependent verification. All four categories are supported by the installed testing standard, Org schema and validator; keep each test's identity and include AT in inventory and readiness checks.

** Decisions and unresolved blockers

- *One letter file per selected recipient*; PDF is the default and =--to= remains a recipient filter.
- Manuscript output remains a required target filename; its extension selects the writer.
- *No known external prerequisite blocks definition*. Native layout feasibility remains a delivery risk, especially parity, continuous frontmatter/body transitions and multi-page contents formatting. A demonstrated inability to express a required feature blocks conformance and requires an explicit amendment, not a warning-only downgrade.

* Test Definitions
:PROPERTIES:
:CUSTOM_ID: test-definitions

** Shared regression method

- Boundary :: Invoke the public in-process application for the case matrix, plus the built executable outside the checkout for packaging. Use real local Pandoc for successful ODT conversions and Go ZIP/XML decoders for native artefact assertions. DOCX dependency cases run with Pandoc absent and with an executable trap; neither may call it.

- Inputs :: Synthetic fixtures in temporary directories with controlled configuration roots, fonts and clock where date defaults matter. Run every new export assertion for *both DOCX and ODT* unless explicitly a dependency-preservation case.
- Oracles :: Compare ordered text, semantic nodes, resolved native properties, relationships, fields and package assets. Do not use source-code searches, ZIP byte equality or a text-only round-trip as proof of formatting.
- Failures :: Inject only the process/filesystem boundary for deterministic timeouts, malformed packages, permissions and interrupted writes. Such doubles prove First Folio's failure handling, not Pandoc conformance.
- Retention :: All RTs run in =make test=. New-behaviour RTs require meaningful RED before implementation. Preservation cases may initially be GREEN. Required dependencies must not silently skip coverage.

** Labelled reference fixtures
:PROPERTIES:
:CUSTOM_ID: reference-fixtures
:END:

- Deliverable :: Retain *three small logical fixtures*: manuscript typography/content, manuscript book layout, and a two-recipient letter. Keep Markdown/Org equivalents for manuscript source parity; reuse the same content across a few named configuration profiles instead of creating a document per setting. These are maintained delivery artefacts used by RTs, OTs and UTs, not throwaway demonstration files.
- Visible expectations :: Each specimen describes its intended appearance using *concrete font names, sizes and measurements*. For example, a header can read "Header: Iosevka Publish 10pt; 20mm from the top page edge; 5mm clearance to body content." Its profile must explicitly set the matching font and geometry. Specify which edge or baseline is measured; do not conflate page margin, header position and body clearance.
- Other examples :: Label body/quote/code samples, heading positions, list/table gaps, page-number behaviour and letter blocks similarly. A footnote should state its verified expected family and size and identify whether these are inherited or fixed. Do not invent a footnote font setting or assume the illustrative 8pt value is the existing contract.
- Independent oracle :: Expected labels and a companion checklist are reviewed against the fixture's YAML and authoritative semantics, *not populated from the exported document or the renderer under test*. A shared rendering bug must not produce both the output and its expected description. Profiles that change values must have matching labels or clearly identified alternate expected results.
- Configuration location :: Manuscript Markdown fixtures exercise supported YAML frontmatter, including metadata and =folio:= overrides. Org manuscripts and letters use the corresponding local =script.yaml=, because this change does not add YAML frontmatter to those source formats. Each UT names the actual file/profile and source of every setting it proves.
- Coverage checklist :: Enumerate *every supported leaf YAML key* in the manuscript and letter contracts, including the six properties of each font role. Map each key to fixture, named profile, visible specimen/marker, exact expected value, named UT and relevant RT. Wildcard families below must be expanded in this checklist. Record absent/empty/disabled/inherited cases explicitly; they cannot be proved merely by displaying a label.
- Profiles :: Reuse labelled content for base, customized and contrasting profiles. Include disabled features, missing optional fields, inheritance and alternate numbering/parity where a single output cannot show both states. Each profile has exact commands to generate PDF, DOCX and ODT side by side. Keep the set small; do not multiply it by the Cartesian product of settings.
- Fonts and output :: Use bundled or already available redistributable test fonts; no font download/build. Keep generated documents in temporary output, with reproducible commands and durable observations in =validation.org=. Labels are inspection aids, not proof that actual font metrics or spacing match.

** DOCX workflow: native throughout

1. Select DOCX, resolve inputs and configuration through the [[#configuration-cascade][same YAML cascade as the mode's PDF renderer]], and parse with the shared native implementation above. Metadata and dry-run use this same native route.
2. Apply the mode adapter: manuscript roles, generated matter and page policy, or recipient-specific letter composition. Preserve structured editable content.
3. Call the *existing native DOCX serializer used by folio convert*, extended for prose blocks, lists, tables, links, notes and fields. Reuse its native XML, styles, relationships and ZIP assembly in =internal/office=.
4. Apply native sections, running matter and fonts; validate the package and publish atomically. *No step calls Pandoc*, requests a reference DOCX, or discovers a Pandoc API/version. No DOCX-to-other-format round trip occurs.

** ODT workflow: native content, configured Pandoc writer

1. Resolve configuration through the [[#configuration-cascade][same YAML cascade as the mode's PDF renderer]] and parse source natively using the same office mode adapters as DOCX. *Pandoc does not read Markdown or Org* in this route.
2. Project structured content into Pandoc JSON. Resolve semantic roles and the effective YAML into named ODF styles and the *existing native-generated ODT reference package*. Compatibility/version probes, if required, belong only to this ODT branch and share its process bounds.
3. Invoke the *existing shared configured Pandoc ODT writer* with JSON input, ODT output and that generated reference. Pandoc creates the initial ODT content package; it does not choose the application's layout from defaults. Do not request a default reference from Pandoc, and do not generate or convert a DOCX intermediate.
4. Validate the writer's ZIP/XML output, then apply native ODF layout that needs postprocessing: page masters, header/footer variants, numbering, fields, generated matter and configured spacing. Preserve the accepted ODT transition limitations.
5. Embed available permitted fonts, validate the final manifest, relationships and package bounds, and publish atomically. A missing/incompatible Pandoc, writer failure or invalid package leaves the affected destination unchanged.

- Ownership :: Shared parsing is below the mode adapters; =internal/office= owns output mechanics and depends on shared config/font value types, not =app=, =manuscript= or =letter=. Mode adapters own their semantics and resolved layout. Keep script-specific presentation separate from prose presentation while sharing parsing and serialization mechanics.
- Verification :: AC063.11 - Parser reuse requires call-path inspection as well as RT063.13 - Shared parser tests. AC063.12 - DOCX independence requires absent/trapping-Pandoc public-command tests. AC063.13 - ODT route requires actual writer invocation and native configuration assertions. RT063.10 protects existing script and PDF/Typst callers. A native DOCX writer alone does not satisfy the end-to-end requirement.

** Publication and resource rules
:PROPERTIES:
:CUSTOM_ID: publication
:END:

- Input :: Regular UTF-8/XML-representable source text, maximum *32 MiB aggregate resolved manuscript input* or letter source. Bound canonical intermediate text/JSON to 128 MiB, semantic blocks to 50,000 and inline nodes to 100,000; maximum nesting depth 128. Check before expensive rendering and reject overflow, never truncate.
- Processes :: Maximum 120 seconds for each Pandoc invocation, 64 KiB captured diagnostics and 128 MiB output. Propagate cancellation and stop the process on overflow. These limits govern the ODT writer and any ODT compatibility probe; the DOCX route has no such subprocess. No retry loop or shell invocation.
- Packages :: Reference/generated XML and individual ZIP members at most 128 MiB, compressed package 128 MiB, expanded package 256 MiB, maximum 256 members. Reuse existing font limits (32 MiB per face, 64 MiB total; bounded discovery). Validate both before and after font packaging; reject duplicate/unsafe member names, invalid XML, missing required parts and broken internal references. External hyperlink relationships may be retained but never fetched.
- Paths :: Reject source/destination aliases including hard links, destination symlinks and nonregular destinations. Generated letter paths must remain inside the selected output directory; reject separators/traversal in prefix. Preflight all recipient and sidecar paths, including duplicate paths under the destination filesystem's case rules, before publishing any output.
- Mode boundary :: These new path, collision and containment rules apply only to DOCX/ODT exports; omitted format and explicit =--format pdf= retain existing letter PDF behaviour.
- Atomicity :: Stage beside each destination with mode 0600, validate, close and rename. Preserve the existing target on any failure before its rename. Clean private references, font extractions and failed staging files on all exits.
- Batch outcome :: Process recipients in existing source order; announce only published files. On later failure, stop and identify the failed target while retaining earlier outputs. Existing selected regular files may be replaced on a successful repeat. No batch rollback or promise of cross-file atomicity.
- Sidecar outcome :: Validate both paths before rendering. Publish the manuscript first, then the requested barcode SVG atomically. If sidecar publication fails, return non-zero and explicitly report that the manuscript was published; preserve any prior sidecar. This retains the existing publication order without promising an unavailable multi-file transaction.

** Architecture impact

*** Security impact

- Trust boundary :: Source text, YAML, local font metadata and Pandoc output are untrusted. Validate size, encoding, depth, ZIP/XML structure, relationships and paths before publication.
- Data :: Manuscripts and correspondence may be private. Use private temporary files and output permissions; no raw source dumps in diagnostics, no credentials, macro content or arbitrary embedded files.
- Access :: No network requests, downloads, uploads, executable filters, font installation or office automation. Hyperlinks remain inert document data during conversion. Reject raw active content before passing it to a writer.
- Mitigation :: Fixed subprocess arguments, bounded processes, generated references and structured serializers prevent source/config values becoming executable instructions. Existing font licensing/embedding-permission handling remains mandatory.

*** Maintainability and portability

- Keep *mode semantics separate from package mechanics*. Shared extraction must preserve script behaviour, and successful package tests must be supplemented by actual reader evidence.
- Document tested Pandoc and reader versions during delivery. Validate a compatible JSON API version only at the shared ODT projection boundary rather than assuming all installations accept one hard-coded version. No DOCX command performs a Pandoc version or JSON-API probe.

- No speculative plugin interface, service, new shell helper or Rust component is required. File names, private helper signatures and test organization remain routine implementation details within these boundaries.
