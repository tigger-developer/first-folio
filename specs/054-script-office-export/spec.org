* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome
- Stage plays and screenplays gain *editable DOCX and ODT exports* that
  *preserve script content and configured formatting*.
** Before
- Scripts already have a *typed event intermediary* and resolved configuration;
  their formatted outputs are Typst and PDF.
** After
- Org, Markdown and Fountain scripts export to both office formats using
  British, US stage-play and screenplay layouts.
- Exported text, styles, tables, footnotes, explicit breaks and running matter
  remain editable; office applications own automatic pagination.
** Changes
- A *separate office adapter* maps existing events to styled Pandoc documents
  and applies resolved layout through native office properties.
- DOCX/ODT become output formats in =folio convert=, including redirected stdout.
** Unchanged
- *PDF and Typst rendering remain untouched*: no renderer refactor, new
  intermediary, or Pandoc dependency on those routes.
- Existing text conversion, configuration precedence, manuscripts and letters
  retain their contracts. Office formats remain *export only*.
** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:
- Unsupported active formatting *fails explicitly*, rather than producing an
  apparently successful export with simplified formatting.
- Missing Pandoc, conversion failure or invalid output leaves *no partial
  target* and preserves any previous target. Binary terminal output is guarded.
- Empty scripts and absent title metadata remain valid; hidden elements stay hidden.
** Decisions
- Reuse =play.Document= and =config.Config=, not generated Typst or the public
  Markdown emitter. Pandoc owns content serialization; a bounded Go ZIP/XML
  adapter owns formatting that custom styles alone cannot convey.
- Preserve layout rules, *not identical automatic line/page breaks* across
  Word, LibreOffice and Typst. Do not embed fonts or flatten content into images.
** Next step
- Definition review and operator sign-off precede delivery.

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem
Script submissions and editing workflows need DOCX/ODT without *recreating the
existing script formatting in a word processor*. Converting the current public
Markdown output with generic Pandoc defaults does not carry the resolved layout.

** Outcome
A single =folio convert= invocation produces an *editable, formatted script*
in either office format from each existing script source format.

** Scope
*** In scope
- DOCX and ODT *export only*, from Org, Markdown and Fountain scripts.
- British stage-play, US stage-play and screenplay styles; existing effective
  script layout and metadata, render toggles, inline formatting and Unicode.
- Native editable content and layout, output lifecycle, diagnostics and packaging.
*** Out of scope
- DOCX/ODT import, manuscript/letter exports, GUI work, PDF conversion through
  Pandoc, font installation/embedding, and user-supplied reference documents.
- New script configuration semantics or making previously unused keys effective.
*** Unchanged
- *No changes to the PDF/Typst renderer*, its template, helper semantics or
  compilation path. No refactor of shared rendering to accommodate office output.
- Existing parsing, event model, text emitters and configuration precedence.

- Formatting means preserving the *effective current renderer's layout rules*,

- Keep the significant intermediate semantic model *unchanged*.

- Office layout engines may reflow content. Requested font families remain
  declared; font substitution by a consuming application is outside export control.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture and flow
1. Existing conversion reads and parses the script, loads config, applies
   metadata, character-name policy and render filtering exactly as before.
2. Only DOCX/ODT dispatch to a new Go office adapter taking =play.Document=,
   =config.Config= and the selected output format.
3. Build a *Pandoc JSON AST* of ordinary paragraphs/spans, native tables and
   notes with stable named styles. Discover the installed Pandoc API version
   through a bounded empty JSON conversion; do not hard-code a version tuple.
4. Invoke Pandoc's DOCX/ODT writer directly. Apply formatting to its completed
   package using Go =archive/zip= and =encoding/xml=, then validate and publish.
5. Use a per-invocation OS temporary directory, removed on success and failure;
   file publication uses a same-directory staging file and atomic rename.

- Reuse :: Existing parsers/events/config remain the single source of truth.
  Do not route through the public Markdown emitter, generated Typst, manuscript
  block model or a generic replacement rendering framework.
- Ownership :: Pandoc serializes ordinary document content, tables and notes.
  The new adapter owns named-style definitions and native page/layout structures.
  Use the writer's shipped defaults with an isolated data directory; do not load
  personal defaults, filters or reference documents.
- Inline content :: Convert the existing supported inline meanings into typed
  AST inlines; any helper reuse must leave its implementation unchanged. Do not
  pass source/config strings as RawBlock/RawInline. Escape via JSON/XML serializers.
- Simplicity :: One event-to-AST operation shared by both writers, with two small
  format-specific package/layout mappings. No new service, runtime, third-party
  office library or independently maintained style presets.

** Layout mapping
:PROPERTIES:
:CUSTOM_ID: layout-mapping
:END:

The normative scope is the current *effective script renderer*, not every
configuration key in the exhaustive shared preset. This table defines the
office equivalent; reference implementation files establish current defaults.

| Area | Required office representation |
|------+--------------------------------|
| Fonts | Native role styles declare family, size, effective weight/style, horizontal stretch and tracking. Regular/bold and regular/italic defaults work in both formats. Values lacking an exact native representation are rejected, never thresholded or approximated. |
| Lengths | Convert pt/mm/cm/in using standard physical units; em uses the effective role font size. Preserve sign and round once to native precision. Percentages use the same applicable layout extent as the current renderer. |
| British speech | Borderless two-column native table: cue column equals configured dialogue wrap width, remainder holds parenthetical and dialogue; separate character styles preserve speaker/instruction/dialogue fonts. Preserve line breaks and allow long content to flow. |
| US/screenplay speech | Separate cue, optional instruction and dialogue paragraphs; dialogue left/right insets match current pad geometry; speaker inset is additional within that area. Apply current speaker/instruction alignment and role fonts. |
| Directions/transitions | Native paragraphs preserve effective before/after spacing, inset, alignment, font and effective casing. |
| Act/scene/intro headings | Named paragraph styles preserve current font/alignment/spacing/casing; explicit act breaks follow current dedicated/compact first-act rule. |
| Props/cast/footnotes | Props retain current centred bold italic layout and fixed spacing; cast uses editable two-column 30%/70% table; footnotes use native note content with preserved inline formatting. |
| Title | Dedicated title page only when enabled and title exists; compact mode renders title metadata above content, without suppressing natural pagination. Preserve title vertical offset, alignment, role fonts, subtitle/author spacing, multi-line author prefix and date/version slot positioning. |
| Paper/margins | Resolve paper name to native width/height; preserve side margins. Body top/bottom use enabled running matter edge distance plus clearance as in current renderer; dedicated-title page follows its current margin rule. Unknown paper names fail explicitly. |
| Running matter | Native first/odd/even header/footer definitions and page fields, preserving effective font, alignment, edge distance, clearance, title suppression and separate intro/body variants. Unknown tokens stay literal; manuscript-specific tokens stay empty. Section/page-style boundaries must not introduce an extra page or reset physical numbering. |

- Native differences :: DOCX uses WordprocessingML styles/sections/fields;
  ODT uses ODF text/paragraph styles, page layouts, master pages and fields.
  Generate only the properties needed for the current script contract; preserve
  unrelated Pandoc package members and valid relationships/manifest entries.
- Format ceiling :: DOCX cannot natively express every arbitrary numeric font
  weight as distinct from regular/bold. Such active values fail for DOCX;
  defaults must export. Apply the same no-approximation rule to ODT properties
  not representable by its native format. Publish the exact support table during
  delivery; do not weaken this requirement to obtain a passing test.
- Pagination :: Explicit breaks and composition rules are preserved. Native
  application line wrapping/page count, font substitution and field refresh are
  not required to reproduce Typst's exact pagination.

** Interfaces and failure behaviour
- Commands :: =folio convert play.org play.docx=,
  =folio convert play.fountain play.odt --style screenplay=,
  and redirected =folio convert play.md --to docx=.
- Selection :: Extend the format registry with two write-only formats; retain
  existing target-extension precedence and =folio.default-format= behaviour.
- Publication :: Fully build and validate output before target replacement or
  binary stdout. Match existing =--force= terminal guard, with format-specific
  diagnostics; do not alter its PDF branch. Source/target identity is rejected
  for office export. Destination symlinks are rejected for office export to
  avoid ambiguous replacement; existing-route semantics do not change.
- Process :: Fixed arguments and structured stdin, no shell; at most two
  Pandoc calls per export (API discovery and writer), each with a 120-second
  deadline, no retries. Bound captured diagnostics to 64 KiB.
- Resource bounds :: Office-only source input at most 32 MiB; intermediate and
  final packages at most 128 MiB each; at most 256 package entries and 256 MiB
  total uncompressed XML/package data. Check limits during reading/generation.
  Reject overflow with nonzero status; leave existing routes' limits unchanged.

** Design decisions and verification
- *Keep PDF untouched* :: Implementation review inspects the renderer/template
  diff; [[#rt-054-4][RT054.4 - Route preservation]] verifies public behaviour.
- *Styles plus native layout* :: Pandoc style transport was probed locally;
  [[#rt-054-2][RT054.2 - Native properties]] and
  [[#ut-054-1][UT054.1 - Application review]] establish complete fidelity.
- *No lossy fallback* :: [[#rt-054-3][RT054.3 - Failure boundaries]] covers unsupported
  values and atomic publication. A missing native mapping is a delivery blocker,
  not authority to simplify required default layouts.

** Routine details left to implementation
- New adapter filenames, typed AST structs and XML helper decomposition.
- Native identifiers and relationship IDs, with collision-free deterministic allocation.
- Test fixture naming and reuse of existing public executable helpers.

** Security impact
- Threat boundary :: Untrusted source/config becomes structured JSON/XML and a
  local subprocess input. No new remote access or data-sharing permission.
- Mitigations :: Fixed arguments, no raw executable markup, isolated Pandoc
  data directory, no resource/media resolution, bounded process/package data.
  Read ZIP members in memory without extracting paths; reject duplicates,
  unsafe names, malformed XML and unexpectedly external relationships.
- Data :: Scratch files use private permissions; cleanup removes only owned
  invocation state. Do not log script bodies, read secrets or embed macros.
- Dependency :: Reuse installed Pandoc; no new application library dependency.
